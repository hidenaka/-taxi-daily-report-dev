# 設計: 自前 PDF↔地図 対応点ジオリファレンスツール

- 日付: 2026-05-27
- 対象: 京北交通の管理者（編集モード内のサブ機能）
- 関連: 既存 stands feature の `approaches[].line` を実地図に正確に乗せるための補助機能

## 背景・課題

既存実装で `approaches[].line` を「ピンから半径100mの直線2点」で機械生成したが、これは実際の道路上に乗っておらず、地図に表示すると「ビルの中の空中の短い線」になる。47施設すべて同じ品質で、ドライバーの現場利用に耐えない（dev実機で確認済み）。

これまでに試した解決策と行き詰まり:
- **AI自動ジオリファレンス（MatchAnything）**: 残差1m級の精度は出るが、HuggingFace無料GPU枠で42件をまとめて処理できない／ローカル実行は重みファイル未公開で不可
- **Leaflet.DistortableImage で四隅ドラッグ**: 手描き略図と歪み大で合わせづらく、42枚は重労働
- **Claude(私)が画像目視で座標推測**: ピクセル位置の精度が出ず、誤差50〜100m

行き詰まりの本質は「**画像同士をピクセル単位で完全自動合わせ**」を求めたこと。これに対し、**3〜4点の人手対応点でホモグラフィを計算する古典手法**は確実に動作するが「自前で作る」発想がなかった。

## ゴール

各施設で**ユーザーが3〜4点を両画面でクリック**することで、PDF内に描かれた進入線が**実地図の正しい緯度経度に変換**されて `approaches[].line` に保存される。47施設×3点クリック＝合計**20〜30分のユーザー作業**で全件正確化する。

## ユーザーの要求への対応

| 要求 | 充足手段 |
|---|---|
| 「進入向きが一目で分かる」 | 道路上に正確な進入線が描画される |
| 「特定のところだけ」 | 3〜4点だけ正確に取れば線全体が決まる（全画素合わせ不要） |
| 「自作で・外部AI不要」 | OpenCV等もJS自前計算（最小二乗法）で十分。Nominatimなど外部API依存ゼロ |

## スコープ外（今回やらない）

- 完全自動ジオリファレンス（MatchAnything等の再導入）
- PDFを地図に重ねて表示する機能（既存 Leaflet.DistortableImage はそのまま残置・別機能）
- PDF以外のフォーマット対応（svg/png 等）
- マーカー（入口・タクシーベイ等）の対応点指定機能（最初は進入線のみ）

## 確定した設計判断

| 論点 | 決定 |
|---|---|
| 進入線の指定者 | **Claudeが事前にPDF内ピクセル座標を抽出**して `pdfLines` に保存 |
| 対応点の数 | 最低3点（アフィン変換）、推奨4点以上（ホモグラフィでより正確） |
| ユーザー作業 | 各施設で「PDFの目印→地図の同じ場所」を3〜4回両画面クリック |
| UI形式 | 既存編集モードに「📐 PDF合わせ」モード追加。左右分割の専用ビュー |
| 計算 | 純JS関数（最小二乗法によるホモグラフィ計算）。外部ライブラリ不要 |
| 結果 | `approaches[].line` を上書き保存→既存ビューアで自動的に正しい位置に描画 |
| 既存資産 | `pdfLines` を空にすると従来の `line` データを保持（後方互換） |

```json
{
  "label": "六本木通り側から進入",
  "road": "六本木通り",
  "bearing": 180,
  "turn": "either",
  "hint": "センターループ入口A→一方通行で左へ",

  "pdfImageRef": "roppongi_hills-1.jpg"  // どのPDFに描かれた線か
```

`pdfLines` が空（または `pdfImageRef` 不一致）の施設は変換不要。`line` がそのまま使われる。

## UI仕様

### 起動
編集モードで施設を選択し、「📐 PDF合わせ」ボタンをタップ。`pdfLines` を持つ施設のみ有効。

### レイアウト
- 全画面オーバーレイ。左右50%分割（モバイルは縦分割に切替）
- 左：PDF画像（既存 `tools/data/stands-ref/<id>-1.jpg`）。クリックで赤いマーカー（番号付き）
- 右：既存 Leaflet 地図（施設pinを中心にズーム18）。クリックで青いマーカー（番号付き）
- 下にツールバー：
  - 「対応点 [1/4]」インジケータ
  - 「↩ やり直し」（最後の点を取り消す）
  - 「変換」（3点以上で有効になる。計算→プレビュー表示）
  - 「💾 保存」（変換結果を `approaches[].line` に書き込む）
  - 「✖ 閉じる」

### 操作の流れ（1施設あたり）
1. 「📐 PDF合わせ」起動
2. PDFで目印（六本木通り×外苑東通りの交差点等）をクリック→赤①
3. 地図で同じ交差点をクリック→青①
4. 別の目印で②、③、（推奨④）を繰り返す
5. 「変換」→地図上に変換後の進入線がプレビュー表示
6. 良ければ「💾 保存」→Firestore反映→閉じる

### エラー処理
- 対応点が3点未満で「変換」を押した→「最低3点必要」アラート
- 対応点が一直線上に並んだ（特異）→「目印を3方向に散らしてください」アラート
- 計算結果の進入線が地図表示範囲から大きく外れた→「結果が不自然です。対応点を見直してください」警告

## データフロー

```
1. 私(Claude)が事前作業:
   各PDF画像を読み取り、進入線のピクセル座標を抽出 →
   scripts/data/pdf-lines-keiho.json に47施設分

2. ユーザーが merge-pdf-lines.mjs を実行 →
   seed JSON の approaches[] に pdfLines/pdfImageRef が反映

3. ユーザーが PDF合わせモードを起動 →
   PDF↔地図で3〜4点クリック →
   computeHomography で行列を計算 →
   pdfLines を applyHomography で line に変換 →
   Firestore に保存

4. ドライバーが stands.html を開く →
   既存ビューアが line を読んで地図に進入線を正確に描画
```
