# 設計メモ: 個人プラン商品分割 ＆ 会社移管モデル（2026-05-23）

> 出典: 料金方針ピボット（`.company/secretary/notes/cabis-pricing-pivot-free-model.md`）の壁打ちで確定。
> 関連: 進行中 `feat/free-company-registration`（会社単位の無償フラグ `freeForInvited`）。

## 背景・確定事項
- 入り口は2本立て：A=組合(団体)導入＝ドライバー無料／B=個人サブスク。
- 個人サブスク：シンプル¥700・普通(フル)¥1,000・初月無料・組合割引なし（旧 提携500/KUMIAI/KEIHO 廃止＝LP実装済）。
- データモデル：日報(`drives/{userId}/daily/{date}`)・課金(`subscriptions/{userId}`)・設定はすべて **userId** に紐づく。会社は user doc の **`companyId`** 1フィールド。給与は **現在の `companyId` の会社プロファイルから都度計算**（日報に設定スナップショットは持っていない）。

## Q1. シンプル/普通を「別商品」にする

現状＝¥1,000の単一Stripe価格＋クーポン割引。シンプルは管理付与の隠れ階層。これを自分で選んで契約できる2商品にする。

### 必要な変更
1. **Stripe**：価格を2つ用意 — `simple ¥700/月`・`full ¥1,000/月`（**¥700価格の作成はオーナーのStripe操作**）。
2. **Worker `create-checkout-session`**：`plan`('simple'|'full') を受け取り `STRIPE_PRICE_ID_SIMPLE` / `STRIPE_PRICE_ID_FULL` を出し分け（現状は単一 `STRIPE_PRICE_ID`）。
3. **subscribe.html**：プラン選択UI（シンプル/普通）を追加 → 選択を checkout に渡す。
4. **契約記録/Webhook**：購入プライス→`planId`→tier（'simple'|'full'）を `subscriptions/{userId}` に記録。`js/access-control.js` の tier 判定は実装済みなので**そのまま機能**。

### 注意
- 先日の「表示だけ¥700」からの格上げ。**クーポン撤去はそのまま活きる**。
- 既存¥1,000契約者は影響なし。

## Q2. 移管・会社変更モデル（採用＝案イ）

### 中核原則
**アカウントは引っ越さない。同じ userId のまま `companyId` と課金だけ切り替える。** 日報・設定・課金は userId 紐づきなのでデータ移行ゼロ。

### 統一ルール：移管/会社変更時は「移行先の今の状態」で再判定
| 移行先 | 課金 | 設定（今後） |
|---|---|---|
| 組合導入あり（`freeForInvited` 等で無料対象） | 無料化。個人課金は **期末で解約**（返金・日割りなし＝規約準拠、有料期間使い切り後に無料へ継ぎ目なく移行） | 移行先の会社プロファイルに合わせる |
| 組合導入なし（普通の会社） | 無料にならない → 使い続けるには個人課金 | 移行先プロファイルがあればそれ／なければ要構築 |

### 2原則
1. **無料は「会社」に紐づく**。会社を出たら無料終了（転職先が未導入なら個人課金に戻る／新会社が導入するまで）。
2. **会社変更のたびに「移行先の導入状態を見て無料/課金を再判定する関数」を1つ**走らせる（本人が招待URLを踏んだ時・会社切替時）。

### トリガーは本人起点（プライバシー設計の帰結）
運営は「誰がどの会社か」を知らない（匿名）。よって管理側一括移管は不可。**本人が会社の招待URL(`?company=slug`)を踏む → アプリが「個人課金中＋この会社は無料対象」を検知 → 「会社アカウントに切替（以後無料）？」を提案 → 承認で実行**。`freeForInvited`(WIP)の自然な延長。

### 過去の手取り＝案イ（記録時点の会社で固定）
- 課題：給与は現 `companyId` から都度計算 → 会社を変えると**過去の手取りまで新歩率で書き換わる**（転職で不正確化）。
- 採用：**各日報に「その時の会社（companyId、必要なら設定スナップショット）」を刻む** → 会社をまたいでも過去は正しいまま。今後ぶんだけ移行先に合わせる。
- 影響：`drives/{userId}/daily/{date}` 保存時に `companyId`（＋将来は給与設定スナップショット）を付与。給与計算は「その日のレコードに刻まれた会社設定」を優先。既存レコードは現 `companyId` で1回バックフィル。

## 実装順（フェーズ）

### Phase 1: 個人プラン商品分割（Q1）
- Stripe ¥700 価格作成（オーナー）→ Worker plan出し分け → subscribe.html プラン選択 → tier記録。
- 自己完結・収益直結。先行で出せる。

### Phase 1.5（軽い先行投資）: 日報に `companyId` を刻む（書き込みのみ）
- 以後の日報レコードに `companyId` を必ず付与（計算ロジックは未変更でもよい）。
- 早めに入れるほど、後で履歴を守れる。低コスト。

### Phase 2: 個人→組合無料への移行（Q2 イベント②）
- `freeForInvited` 完了が前提。招待URL検知 → 切替提案 → Stripe期末解約＋無料(active)化＋`companyId`セット。
- 多くは「同じ会社のまま無料化」で過去ズレが小さい。

### Phase 3: 会社をまたぐ正確な履歴＋転職対応（Q2 案イ本体／イベント③）
- 給与計算を「レコードに刻まれた会社設定」基準に切替＋既存バックフィル。
- 会社変更時の無料/課金 再判定関数を完成（転職先の導入有無で分岐）。
